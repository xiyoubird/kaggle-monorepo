# 03 · M2 基线结果与"可信度校准"

## 数据长什么样（EDA 结论）

| 项目 | 值 |
|---|---|
| 训练集 | 699,635 行 × 22 特征 + 1 目标 |
| 测试集 | 299,844 行 × 22 特征 |
| 目标 | `satisfaction`（布尔），True = 满意 |
| 正类比例 | **0.443573** |
| 缺失值 | 只有 `Arrival Delay in Minutes` 有 292 个（0.04%） |

特征可以分成三组，这决定了后面的特征工程方向：

1. **13 个 0–5 分的问卷打分项**（WiFi、座椅舒适度、在线登机……）。
   注意 0 分在原始问卷里表示"没使用/不适用"，不是"最差"，
   所以 0 的分布本身是有信息的。
2. **3 个连续量**：年龄、飞行距离、出发/到达延误分钟数（严重长尾）。
3. **4 个类别**：性别、客户类型、出行目的、舱位等级。
   其中舱位和出行目的与目标的关联极强（商务舱满意率 72.5%，
   经济舱仅 16.8%）。

### 一个差点犯的错

我第一版 EDA 脚本打印

```
正样本占比: 0.5564
```

这个数字是**错的**。原因是我用 `value_counts().iloc[0]` 当正类，
而 `value_counts` 是按出现次数降序排的，`iloc[0]` 拿到的是 False。
正确做法是显式指定"正类是哪个值再算比例"。

> 这件事值得记下来：**AUC 不会因为我把正类搞反而变差**（把预测取反也是 0.5 对称的），
> 所以我不会从指标上察觉这个错误。但后面凡是涉及"正类"的解释
> （比如提交前要不要校准截距、怎么解释特征重要性）都会错。
> 顺带一提，它也解释了一个现象：`sample_submission.csv` 里所有行
> 都是常数 **0.443573**——那正是训练集的正类比例，Kaggle 用它做占位符。

## 关键一步：本地分数可信吗

这是整个项目里最值得单独记录的一步。做法是：把基线提交一次，
然后比较**本地 OOF** 和**线上公开榜分数**。

| 指标 | 值 |
|---|---|
| 本地 OOF AUC | 0.958910 |
| 线上公开榜 AUC | 0.958430 |
| 差值 | **-0.00048** |

结论：两者高度一致，偏差 0.0005 以内。

为什么这件事比"分数是多少"更重要：

- 公开榜只用了 20% 的测试集（约 6 万行），这个规模本身就有约
  ±0.0005 的统计波动；
- 从现在起，我可以**只看本地 CV 就做决策**，把每天 10 次的
  提交额度留给真正的里程碑验证，而不是当成调参工具。

如果当初偏差很大（比如 0.01），说明训练/测试存在分布差异或提交格式有问题，
那必须先解决它，否则后面所有实验都是在优化一个错误的目标。

我们的 0.95843 排在第 **346** 名，略低于中位数。

两个重要解读：

1. **分数高度密集**：从第 1 名到中位数只差 0.0028。
   这类比赛最后拼的是细节，不是"用哪个模型"。
2. **但 0.0028 是实实在在的差距**：它意味着从第 346 名到前 10 名。
   有明确的提升空间，值得认真做。

## 下一步的三个假设

排名靠前的队伍比我们多做对了什么？我列了三个可验证的假设：

| 假设 | 验证方式 |
|---|---|
| H1 外部原始数据能补回真实信息 | 加入 `data.csv`，扫描权重 |
| H2 特征工程能提炼出新的信号 | 加打分聚合、延误、比例类特征 |
| H3 模型容量/超参不够 | 提高 `num_leaves`、降低学习率 |

顺带一个必须检查的 H0：**合成数据是否按 `id` 顺序生成**，
导致 `id` 与目标存在虚假相关。这是 Playground 系列里出现过的经典陷阱。
